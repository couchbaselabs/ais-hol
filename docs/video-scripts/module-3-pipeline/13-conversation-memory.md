# Conversation Memory

**Module:** Building a Pipeline | **Level:** Intermediate
**Runtime:** ~7 min | **Tab:** `history`

---

## Hook

*"What did I just ask you?"* — in the Simple Chat tab, the model has no idea. Every message is a fresh start. Real applications need the model to remember: the user's name, what they asked three turns ago, the context they established at the start of the session. That requires storing conversation history and injecting it into every prompt.

---

## Concept

LLMs are stateless — they have no memory between API calls. Conversation memory is an application-layer concern: you store the history, you inject it into the prompt, you manage what gets kept and what gets dropped.

The simplest approach: store every message in a database keyed by session ID. Before each LLM call, fetch the history and prepend it to the messages array. The model sees the full conversation and can reference anything said earlier.

The problem: history grows without bound. A long conversation eventually fills the context window. You need a strategy for managing history length:

**Truncation**: Keep only the last N messages. Simple, but the model loses early context (like the user's name or the task they defined at the start).

**Summarisation**: Periodically summarise the conversation history into a compact paragraph. The model gets the gist of earlier turns without the full token cost. This is what this tab does — using Capella's built-in `ai_summary()` SQL++ function to summarise history inside the database.

**Sliding window with pinning**: Keep the first N messages (important context) and the last M messages (recent context), dropping the middle. A reasonable compromise.

## Code Deep-Dive

Messages are stored in Couchbase as simple documents:

```python
async def add_message(session_id: str, content: str, role: str):
    doc = {
        "session_id": session_id,
        "role": role,
        "content": content,
        "timestamp": datetime.utcnow().isoformat(),
    }
    collection.upsert(str(uuid.uuid4()), doc)

async def get_conversation_history(session_id: str, limit: int = 20):
    result = cluster.query(
        f"SELECT role, content, timestamp FROM ... "
        f"WHERE session_id = $1 ORDER BY timestamp ASC LIMIT $2",
        QueryOptions(positional_parameters=[session_id, limit]),
    )
    return [r for r in result.rows()]
```

Before each LLM call, history is fetched and formatted into the messages array:

```python
history = await get_conversation_history(session_id)
messages = [{"role": "system", "content": system_prompt}]
for msg in history:
    messages.append({"role": msg["role"], "content": msg["content"]})
messages.append({"role": "user", "content": current_message})
```

For long conversations, history is summarised using Capella's `ai_summary()` — an LLM call that runs inside the database engine:

```python
async def summarize_conversation(session_id: str) -> str:
    result = cluster.query("""
        SELECT RAW ai_summary(
            ARRAY_AGG(role || ': ' || content ORDER BY timestamp ASC)
        )
        FROM `bucket`.`scope`.conversations
        WHERE session_id = $1
    """, QueryOptions(positional_parameters=[session_id]))
    rows = [r for r in result.rows()]
    return rows[0] if rows else ""
```

The summary replaces the raw history in the prompt — same information, far fewer tokens.

## Key Takeaways

- Conversation memory is an application concern — the LLM is stateless, you manage the history.
- Store messages in a database keyed by session ID; fetch and inject them before each call.
- History grows without bound — you need a strategy: truncation, summarisation, or sliding window.
- Capella's `ai_summary()` SQL++ function summarises history inside the database — no extra API call from application code.
- The semantic cache still applies: a cache hit skips both history lookup and the LLM call entirely.
